# Safe Change Workflow (Windows/Web-Jenkins-Unity)

## 0. 目标
- 新功能优先，但绝不破坏已有功能。
- 每次改动必须“可验证、可回退、可定位”。

## 1. 改动边界
- 单次只做一个功能点，不混改 UI 文案/布局/业务逻辑。
- 禁止在同一提交里顺手清理乱码、重构、改命名（除非用户明确要求）。
- 若发现历史脏数据或乱码：先记录，不在当前功能任务里处理。

## 2. 编辑策略
- 优先最小补丁（最少行数、最少文件）。
- 涉及字符串拼接的前端 JS：
  - 禁止复杂引号嵌套拼接。
  - 优先模板字符串或 DOM API（createElement）。
- 非 ASCII 文案改动需谨慎：若文件存在编码风险，优先用 ASCII 占位后再统一处理。

## 3. 强制检查（每次改完必做）
- Python 文件：`python -m py_compile <file>`
- 页面内嵌 JS：
  1. 从后端模板“渲染后”抽出 `<script>`
  2. `node --check rendered.js`
- 若任一步失败：不得重启服务，不得交付，先修到通过。
- 检查通过后、交付前：必须先提交再推送，禁止只 push 不 commit。
  - 必做：`git add` -> `git commit -m "<message>"` -> `git push origin <current-branch>`。
  - 若本次改动涉及多个仓库（如 `E:\maclient` 与 `E:\web\apk-site`），每个仓库都必须分别完成一次提交与推送。
  - 禁止把 `apk-site` 的改动只记在 `maclient` 仓库里，或反之。

## 4. 运行验证
- 重启服务后必须检查：
  - `GET /health` = ok
- 新功能必须提供“可见反馈”：
  - 按钮点击后至少出现 loading/success/fail 文案之一。
- 至少验证 1 条正向路径 + 1 条失败路径（例如接口失败时提示）。
- 任何功能修改完成后，必须执行一次服务重启再交付；禁止“未重启仅靠代码静态检查”即宣称完成。

## 5. 控制台报错处理规范
- 用户给出 console 报错后：
  - 先按行号定位（文件/行/列）
  - 只修该报错链路
  - 修复后再次跑 `node --check rendered.js`
- 禁止“未复现先大改”。

## 6. 回滚机制
- 改动前保留基线文件副本（同目录 `.bak` 或已知 clean 版本路径）。
- 若出现页面不可用：
  - 立即恢复基线
  - 再做增量补丁
- 禁止连续叠加修补超过 2 轮不清理；第 3 轮必须回基线重做。

## 7. 交付格式（必须包含）
- 改了哪些文件
- 做了哪些命令级校验（列命令和结果）
- 用户如何复测（3 步内）
- 若未完成：明确卡点和下一步

## 8. 禁止项
- 不验证就说“已修复”
- 只验证源码，不验证渲染后 JS
- 将多个需求混在一次补丁里
- 发现报错后继续叠加无关改动

## 9. 对外文案与本地化
- 面向用户可见内容必须为中文：按钮文字、状态提示、接口说明文案、错误提示、帮助文案。
- 若为临时调试文案，提交前必须恢复为中文正式文案。

## 10. 兼容性与影响面评估
- 做新功能时，必须评估已有调用方是否复用该接口/逻辑（页面、脚本、定时任务、其他模块）。
- 新增或修改接口参数时：
  - 默认向后兼容（旧参数可继续使用）。
  - 变更前给出影响清单与回归点。
- 禁止只修“当前页面可用”而忽略同接口其他入口。

## 11. 架构与可维护性约束
- 新功能禁止把大量逻辑堆入单一脚本/单一函数。
- 需要按职责拆分：路由层、服务层、前端交互层分别处理。
- 前端交互代码超过可读阈值时，优先拆为独立函数（初始化、事件绑定、请求、渲染）。
- 后端新增能力优先放在 service 层封装，路由仅做参数校验与编排。

## 13. 设计图驱动 UI 的额外硬规则（覆盖 §1 最小补丁原则）

当任务涉及 `docs/design_assets/` 设计图、用户 @ `design-faithful-ui`、或要求 1:1 / 严格按设计还原时：

- **必须**同时遵守 `.cursor/skills/design-faithful-ui/SKILL.md` 与 `.cursor/rules/design-faithful-ui-rule.md`
- **视觉未通过浏览器对照设计图验收前，禁止交付成品**，即使功能已可用
- 设计冲突时 **重写页面/CSS**，不得在同一 CSS 文件连续叠「fidelity pass」；§6 连续 2 轮失败即回 baseline 重写
- 模块 spec 中 token 表 / 图标清单 / 文案清单 / **专业验收判定表**未填完 → **禁止写 UI 代码**
- 交付报告必须使用 skill《专业验收报告模板》；结论仅「通过验收」或「未通过验收」；任一 FAIL 不得写「已完成」
- **覆盖 §7 交付格式：** 设计图任务禁止用「做了什么、没做什么」遗留式表述；未通过时只报 FAIL（设计 vs 实际）
- **覆盖 §93：** 设计图任务连续 2 轮专业验收仍多区 FAIL → 须 baseline 整页重写并再验（见 skill），**不是**停手等用户确认后再叠第 3 轮补丁
- **验收 FAIL：** 须进入 **Phase C 验收闭环**（C → C-fix → C，直到**全部**效果图 PASS）——见 skill《Phase C 验收闭环》；**禁止**只输出 FAIL 清单即结束任务（用户明确要求「只验收」除外）
- **执行门禁：** 开工须 skill **G1–G5**；每回合回复前须 **R1–R6**；完工须 **F1–F7** + rule Hard Gate 全勾——见 skill《执行到位的强制门禁》
- **多屏模块：** 须执行 skill **《多屏必验动作清单》** + **《交互抽检表》** + **《画布专项门禁》**；缺一 = 流程 FAIL
- **数据链路：** normalize 不得剥设计字段；demo 升级后须 Browser 复验——见 skill《数据链路与运行时门禁》
- **任务结束条件：** 仅当 skill「屏级 PASS 表」**ALL PASS** 才可结束；FAIL 时 Agent 默认继续开发，不问「需要我继续吗」
- **写代码前：** 须完成 skill **Phase A0 设计图深度读图建档**（见 skill），禁止未读原图直接填表或实现
- **禁止再犯：** 见 `.cursor/rules/design-faithful-ui-rule.md`《历史事故清单》（含 **F 类流程执行**）

- 用户明确要求“回退”时：只允许执行回退，不允许夹带任何试修、优化、重构。
- 回退动作前必须先锁定“唯一回退点”（构建号/时间点/截图节点），未锁定不得写文件。
- **（非设计图任务）** 连续 2 次修复失败后必须停手：输出当前状态、已改文件、下一步唯一动作，等待用户确认。
- 任何让用户重跑 Jenkins 之前，必须先本地通过对应语法检查：
  - Shell：`bash -n <script>`
  - Python：`python -m py_compile <file>`
- 禁止“边改边试”扩散：每轮只改一个链路、一个目标文件集合。
- 若当前改动引发新故障，优先恢复到上一可用状态，再进行下一步。
- 高压场景沟通规则：先确认目标再执行，不做争辩，不给不确定承诺。
- **（非设计图任务）** 交付时必须明确写出“做了什么、没做什么”，避免误解为已完成全量修复。
