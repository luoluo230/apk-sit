# 项目管理架构错误清单与统一设计任务书

更新时间：2026-06-13  
适用范围：项目管理、版本、构建、产物、发布单、审批、拓扑、Agent、服务器、动作执行、诊断、日志  
文档性质：后续产品设计与开发的强制约束

## 1. 结论

当前问题不是少量页面或按钮实现错误，而是“新版统一外壳”和“旧版独立模块”同时存在：

- 页面视觉上进入了同一套项目工作区。
- 版本、构建、发布、拓扑、运维在业务、路由、接口和数据层仍然彼此割裂。
- 发布单尚未成为贯穿交付流程的主实体。
- 项目上下文只是 URL 参数传递，不是真正可切换、可校验的统一上下文。

后续开发不得继续对现有页面做局部拼补。新架构必须以项目交付流程为主线，并删除与新模型冲突的旧页面、旧接口、旧上下文和兼容分支。

统一业务主线：

```text
项目
→ 环境
→ 发布单（交付计划）
→ 版本与 VersionCode
→ 构建与产物
→ 拓扑与运行态
→ 预检与审批
→ 发布
→ 验证与回滚
```

## 2. 已确认错误

### 2.1 产品架构错误

| 错误 | 当前表现 | 影响 | 后续强制规则 |
|---|---|---|---|
| 项目上下文不真实 | 顶部项目控件看似下拉，实际是跳转链接 | 用户无法理解当前操作对象，跨页后上下文可能漂移 | 项目控件必须是真实选择器；环境、渠道、平台、版本上下文必须可见、可切换、可校验 |
| 顶部栏职责混乱 | 顶部混入“创建项目”“新建拓扑图”等页面业务操作 | 全局导航、项目上下文、业务操作没有层级 | 顶部栏只保留导航、项目选择、全局搜索、消息和用户；业务创建入口放到对应页面 |
| 项目总览不是工作入口 | 环境卡主要展示数据，只能继续跳转 | 用户无法从阻断项直接开始或恢复交付流程 | 环境卡必须支持创建发布单、继续处理、查看阻断原因、进入对应处理页面 |
| 发布单不是主实体 | 构建、审批、拓扑、运维动作没有完整关联发布单 | 无法追踪一次交付的完整过程 | 所有交付动作和结果必须关联 `release_order_id` |
| 发布单缺少计划能力 | 只能创建固定目标，不能编辑交付计划 | 用户无法配置发布窗口、构建、拓扑、验证和回滚策略 | 发布单必须区分“可编辑计划”和“不可变执行记录” |
| 导航按技术模块堆叠 | 版本、构建、发布、拓扑、Agent、诊断全部平铺 | 用户不知道操作顺序和模块关系 | 导航按“总览、交付、运行、治理”分组 |
| 环境不是核心运营对象 | 环境状态、版本、拓扑、服务器分散在多个页面 | 无法判断某环境是否具备发版条件 | 项目总览和发布单必须以环境为主要上下文 |
| 运维仍像独立产品 | 运维页面只是套了项目壳层，内部仍采用旧工作台结构 | 同一项目内产生双层产品感 | 运维资产和动作必须项目归属化，并服从统一上下文与交付链路 |

### 2.2 代码与实现错误

| 错误 | 当前表现 | 潜在后果 | 整改要求 |
|---|---|---|---|
| 假下拉和装饰控件 | 项目控件、搜索、部分用户控件只有样式或错误跳转 | 用户误操作，页面看似可用但实际不可用 | 所有可点击控件必须有真实行为、加载、成功和失败反馈 |
| 创建入口隐藏 | 发布单只能在二级中心页面创建 | 项目总览和版本流程被中断 | 总览环境卡、VersionCode 详情和发布单中心均提供语义明确的创建入口 |
| 发布单无法编辑 | 无更新接口、无编辑页面、无计划版本 | 创建错误后只能重新建立或继续错误流程 | `draft` 阶段可编辑；预检后锁定；变更需生成新计划版本或变更记录 |
| 路由归属不统一 | 项目路由、全局 build、全局 ops-platform、全局审批同时存在 | 上下文丢失、权限和审计难以统一 | 项目业务接口统一归属 `/api/projects/{project_id}/...` |
| 旧路由和新路由并存 | GM、stage、旧 build、旧 ops 页面仍存在 | 开发可能误改旧入口，浏览器可能继续服务旧页面 | 新架构落地时直接删除旧入口，不做兼容跳转 |
| 多数据真源 | 项目和版本使用 JSON，发布域使用 SQLite | 无法保证版本、发布单、Bundle 原子一致 | 项目交付相关数据统一进入事务化存储 |
| 上下文字段不统一 | `env_key/env/stage`、`channel_id/channel` 混用 | 筛选错误、请求命中错误环境或渠道 | 内部只使用规范字段；UI 只展示业务名称 |
| ReleaseOrder 未贯通 | 构建、产物、审批、运维动作不强制持有发布单标识 | 无法进行完整审计、恢复和对账 | 构建任务、产物、预检、审批、动作、Bundle、验证全部关联发布单 |
| 状态机与页面动作脱节 | 页面可显示动作但未严格根据状态控制 | 重复发布、跳过预检、非法回滚 | 后端状态机决定允许动作，前端只渲染合法动作 |
| 原生确认框和弱反馈 | 使用 `alert/confirm` 或只有文字提示 | 高风险操作缺乏确认上下文 | 使用统一确认弹窗、风险说明、执行进度和结果反馈 |

### 2.3 数据与状态展示错误

| 错误 | 当前表现 | 风险 | 整改要求 |
|---|---|---|---|
| 空值只显示 `-` | 当前版本、Bundle、拓扑为空时没有解释 | 用户不知道是未配置、加载失败还是权限问题 | 空状态必须说明原因并给出下一步操作 |
| 阻断项不可处理 | 环境卡只显示阻断数量 | 用户仍需逐页寻找问题 | 阻断项必须可展开，并直接跳转到对应修复位置 |
| 技术状态直接暴露 | 页面混用英文原始状态 | 业务用户难理解，同一状态不同页面文案不一致 | 建立统一中文状态字典和语义色 |
| 实时与快照混淆 | 运行态、Bundle 快照、拓扑资产展示边界不清 | 用户误认为历史快照是当前实时状态 | 明确标记“资产、当前运行态、发布快照”及更新时间 |
| 列表摘要不完整 | 构建历史、发布记录只展示有限摘要 | 用户需要反复跳转，无法快速判断 | 摘要页展示关键字段和状态，详情页展示全量记录与日志 |

## 3. 必须提前防止的潜在问题

### 3.1 上下文与导航

- 用户切换项目时仍携带旧项目的 `release_order_id`、版本或渠道，导致访问错误对象。
- 页面允许“全部环境”时执行构建、发布、回滚等精确操作。
- 浏览器返回、刷新或分享链接后，上下文选择器与页面数据不一致。
- 不同页面对“当前环境”的默认值不同，产生误发生产环境风险。
- 全局搜索结果跳入项目页面时未正确重建上下文。
- 左侧菜单激活状态由页面名称猜测，出现多个菜单同时激活或错误激活。

强制要求：

- 每个页面定义允许的上下文粒度。
- 执行动作前由后端重新校验完整上下文。
- 项目切换时清理所有不属于新项目的下级上下文。
- 生产环境操作必须始终显示醒目的生产标识和二次确认。

### 3.2 发布单与状态机

- 发布单编辑后，已完成的预检仍被当作有效结果。
- 构建产物更新后未使旧预检失效。
- 拓扑绑定变化后，发布单仍引用旧解析结果但 UI 未提示。
- 同一目标存在多个并行发布单，导致覆盖、乱序发布或错误回滚。
- 发布过程中页面刷新、网络断开后，前端误认为执行失败并重复提交。
- 发布成功但验证失败时，没有明确区分“已上线但验证未通过”。
- 取消发布单后仍允许构建、审批或发布。
- 生产审批完成后计划还能被修改，导致审批内容与实际发布内容不一致。

强制要求：

- 状态转换由后端状态机集中控制。
- 任何影响发布内容的变更都必须使预检和审批失效。
- 所有执行接口支持幂等键，防止重复提交。
- 发布单详情必须显示状态变化原因、操作者和时间线。

### 3.3 构建与产物

- 一次构建产生的资源、配置、代码、APK 不属于同一个 VersionCode。
- 构建成功但部分产物未上传或 OSS 不可达。
- 页面只展示最新几条构建，隐藏实际失败历史。
- 重试构建后旧产物仍被发布单引用。
- Jenkins 回调晚到，覆盖了新任务的状态。
- 产物被手工替换但校验值没有变化记录。

强制要求：

- 构建和每个产物都关联发布单、VersionCode 和构建任务。
- 发布前验证产物完整性、可达性、校验值和来源构建。
- 构建历史默认展示完整记录并提供分页、筛选和详情。
- 发布单必须明确选择当前采用的构建批次。

### 3.4 拓扑与运行态

- 拓扑资产、绑定关系、当前运行态和 Bundle 快照被当成同一个对象。
- 修改拓扑资产后，已发布 Bundle 的客户端地址被静默改变。
- 发布单解析到拓扑，但对应 runtime 未启动或已经漂移。
- 渠道、环境、大版本覆盖规则冲突，界面未解释最终命中来源。
- 启停服务器等运维动作没有关联发布单或变更单。
- 同一服务器被多个项目或环境错误复用。

强制要求：

- UI 明确区分拓扑资产、绑定规则、运行实例、发布快照。
- 发布单冻结最终解析出的 topology 和网络快照。
- 绑定关系页面展示继承层级、覆盖来源和冲突提示。
- 运维高风险动作必须显示影响项目、环境、发布单和 Bundle。

### 3.5 权限、审批与审计

- 用户拥有项目查看权限却能执行生产发布或服务器动作。
- 审批中心脱离项目上下文，审批人无法判断实际影响。
- 同一用户既提交又批准生产发布。
- 删除项目、版本、拓扑时未提示引用关系。
- 审计日志只记录动作名称，不记录前后差异与业务上下文。

强制要求：

- 权限按项目、环境和动作分级。
- 审批卡必须展示发布计划、产物、拓扑、风险和差异。
- 所有高风险操作记录对象、上下文、前后值、操作者、时间和结果。
- 被发布单、Bundle 或运行态引用的对象禁止直接删除。

### 3.6 UI 与交互

- 页面为了容纳所有功能不断增加 Tab、卡片和右侧栏，最终信息过载。
- 弹窗承载完整业务流程，导致内容溢出和无法恢复操作进度。
- 同一动作在不同页面使用不同文案、图标和颜色。
- 页面显示可点击控件但功能未接后端。
- 加载、失败、空状态与无权限状态使用同一外观。
- 列表密度、字体、状态色由开发人员临时决定，造成模块风格漂移。

强制要求：

- 创建、编辑等短表单使用弹窗；复杂流程和长表单使用独立页面。
- 同一业务实体使用统一卡片、状态标签和操作菜单。
- 设计稿必须覆盖正常、空、加载、失败、禁用、无权限和高风险确认状态。
- 未经设计图和浏览器对比验收，不得宣称页面完成。

## 4. 新架构会不会造成界面混乱

会。如果只把所有模块放入同一个侧栏和页面壳层，而不重新设计信息层级，新架构会比当前更混乱。

必须同时完成以下三层设计：

1. **产品信息架构**
   - 明确模块归属、页面层级、入口和跳转关系。
   - 明确总览页只负责发现问题和进入流程，不承载全部编辑功能。

2. **统一交互框架**
   - 明确顶部栏、左侧导航、上下文条、主内容、右侧辅助区各自职责。
   - 明确什么使用页面、抽屉、弹窗或确认框。

3. **统一视觉系统**
   - 字体、字号、颜色、图标、间距、卡片、表格、状态和反馈必须统一。
   - 设计稿需覆盖各页面的关键状态，而不只是正常数据状态。

结论：**需要由设计师统一输出一整套项目管理设计，而不是继续逐页补图。**

## 5. 建议设计师统一输出的页面

### 5.1 第一优先级：必须先设计，未出图不得开发

| 页面 | 核心目的 | 必须覆盖的关键状态 |
|---|---|---|
| 项目列表 | 创建、查找、进入项目、查看项目健康摘要 | 正常、空项目、无权限、创建中、删除确认 |
| 项目总览 | 以环境卡发现阻断并进入交付或运维流程 | 正常、未配置、存在阻断、处理中、待审批、生产风险 |
| 发布单中心 | 查看和筛选全部交付计划 | 空列表、草稿、执行中、失败、待审批、已完成、已取消 |
| 新建/编辑发布单 | 编辑完整交付计划 | 初始、字段错误、上下文冲突、保存中、被锁定、变更后预检失效 |
| 发布单详情 | 驱动构建、预检、审批、发布、验证与回滚 | 每个状态机阶段、动作禁用原因、执行进度、失败恢复 |
| 版本与 VersionCode | 管理版本并创建发布单 | 无版本、构建中、产物缺失、已关联发布单、已发布 |
| 构建与产物 | 查看完整构建记录和产物完整性 | 排队、构建中、部分成功、失败、取消、产物不可达 |
| 拓扑资产列表 | 管理项目拓扑资产 | 草稿、已验证、运行中、停用、被引用、归档 |
| 拓扑详情/编辑器 | 编辑节点和连接并验证拓扑 | 编辑、校验错误、未保存、运行态对比、引用关系 |
| 拓扑绑定矩阵 | 配置环境/渠道/大版本到拓扑的绑定 | 默认继承、覆盖、冲突、未绑定、变更影响提示 |
| 环境运行工作台 | 查看服务器、Agent、运行态和诊断 | 健康、部分异常、离线、执行中、操作失败 |
| 审批详情 | 审批生产交付或高风险运维动作 | 待审批、批准、拒绝、撤回、内容变更后失效 |

### 5.2 第二优先级：应统一设计

| 页面 | 设计重点 |
|---|---|
| 下载中心 | 产物来源、版本、平台、校验值、二维码和失效状态 |
| 测试设备 | 设备状态、安装版本、最近联调结果和操作反馈 |
| Agent 与服务器 | 项目归属、环境、在线状态、服务、资源和维护状态 |
| 动作执行中心 | 动作目标、风险、执行进度、日志和重试 |
| 节点诊断 | 探活项、依赖关系、异常等级和处理建议 |
| 变更治理 | 变更差异、影响范围、发布单关联和审批状态 |
| 项目日志 | 按发布单、环境、对象和操作者检索审计事件 |
| 项目设置 | 渠道、环境、平台、权限、通知和集成配置 |

### 5.3 可复用设计组件，不需要每页重复设计

- 项目选择器
- 项目上下文条
- 环境状态卡
- KPI 卡
- 状态标签
- 阻断项列表
- 版本组与 VersionCode 行
- 发布单卡片与状态时间线
- 构建记录行与产物卡
- 拓扑小卡片与运行状态
- 服务器与 Agent 状态行
- 审批卡片
- 筛选栏、分页、批量操作栏
- 操作结果 Toast、行内错误、全页错误

## 6. 必须设计的弹窗、抽屉和独立流程页

### 6.1 适合弹窗

- 创建项目
- 添加渠道
- 添加 VersionCode
- 选择已有构建批次
- 低风险删除确认
- 取消发布单确认
- 审批通过/拒绝并填写意见
- 下载二维码
- 简单筛选和列设置

### 6.2 适合抽屉

- 构建详情与实时日志摘要
- 产物详情与校验信息
- 阻断项详情
- 拓扑引用关系
- Agent/服务器快速详情
- 发布或运维动作结果
- 审计事件详情

### 6.3 必须使用独立页面，禁止塞入弹窗

- 新建/编辑完整发布单
- 发布单详情与完整流程
- 拓扑编辑器
- 拓扑绑定矩阵
- 环境运行工作台
- 高风险运维动作执行
- 审批详情和差异审查
- 完整构建历史与日志检索

## 7. 设计师需要交付的统一设计规范

可以，并且建议必须要求设计师统一交付以下内容。

### 7.1 视觉基础规范

- 字体家族及 Windows/Web 可用回退字体
- 字号、字重、行高、字间距层级
- 主色、辅助色、中性色、背景色、边框色
- 成功、处理中、警告、失败、阻断、未配置、禁用语义色
- 间距体系
- 圆角体系
- 阴影体系
- 边框和分割线规范
- 页面最大宽度、侧栏宽度、右栏宽度、响应式断点

### 7.2 图标与切图规范

- 导航图标全套
- 版本、构建、发布、拓扑、Agent、服务器、审批、日志等业务图标
- 状态图标全套
- 空状态插图
- 错误、无权限、未配置、发布成功、发布失败插图
- Logo 和品牌资源
- SVG 优先；必须切图时提供 `1x/2x`、透明背景和使用场景说明
- 每个图标提供名称、语义、尺寸、默认色、激活色和禁用色

### 7.3 组件规范

- 按钮：主要、次要、文字、危险、禁用、加载
- 输入框、搜索框、下拉、级联选择、日期时间、单选、多选
- Tab、步骤条、面包屑、分页
- 卡片、表格、列表、树、时间线
- 状态标签、风险标签、数字徽标
- 弹窗、抽屉、Toast、确认框、错误提示
- 空状态、加载骨架、局部失败、全页失败、无权限

### 7.4 设计源文件要求

- 提供可检查尺寸和 Token 的 Figma 或同类源文件。
- 页面按统一命名和模块分组。
- 每个页面至少提供基准宽屏稿；复杂页面补充窄屏或折叠状态。
- 每个关键页面同时提供正常态和异常态。
- 交互原型标明点击目标、跳转目标、弹窗和返回路径。

## 8. 建议设计交付批次

为避免一次性画大量页面后发现架构错误，设计应分三批验收。

### 第一批：统一框架与主链路

- 全局项目壳层
- 项目选择器和上下文条
- 项目总览
- 发布单中心
- 新建/编辑发布单
- 发布单详情

第一批确认后，才能确定其他页面的导航、入口、状态和视觉母版。

### 第二批：交付与运行

- 版本与 VersionCode
- 构建与产物
- 拓扑资产
- 拓扑绑定矩阵
- 环境运行工作台
- Agent 与服务器

### 第三批：治理与辅助

- 审批
- 动作执行
- 诊断
- 变更
- 日志
- 下载中心
- 测试设备
- 项目设置

## 9. 后续开发强制门禁

### 开发前

- 确认页面属于哪个产品分组和业务阶段。
- 确认页面允许的项目上下文粒度。
- 确认真实数据入口和状态机。
- 确认对应设计稿、组件规范和异常状态图已存在。
- 新实现与旧结构冲突时，删除旧结构，不做兼容保留。

### 开发中

- 不得自行增加设计稿中不存在的顶栏按钮、Tab、右侧栏或弹窗。
- 不得把复杂流程临时塞入弹窗。
- 不得创建只有样式没有真实行为的控件。
- 不得让模块独立维护项目、环境、渠道或平台上下文。
- 不得让构建、审批、运维动作脱离发布单执行。

### 验收前

- 浏览器逐页验证真实路由和真实数据。
- 对照设计图检查布局、字体、字号、间距、颜色、图标和反馈状态。
- 验证所有可见操作均有真实后端效果。
- 验证正常、空、加载、失败、禁用、无权限和高风险确认状态。
- 检查代码中不存在已删除旧入口和旧接口引用。

## 10. 旧规格使用限制

以下旧设计思路与新架构冲突，不得继续直接作为实现依据：

- 将 GM 发版工作台作为独立产品。
- 将运维平台作为独立于项目的产品。
- 将项目顶部栏作为业务创建按钮集合。
- 将发布操作仅设计成临时弹窗或五步发布向导。
- 将构建、版本、拓扑、审批和运维动作设计成互不关联的平级模块。
- 为保留旧功能而继续复用与新架构冲突的旧页面和旧接口。

旧设计图可以作为视觉语言参考，但新架构页面必须重新出图并重新完成交互与状态设计。
