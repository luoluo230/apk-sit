## 2. 设计硬约束

- 该模块不是通用流程图编辑器，而是“受规则约束的结构化拓扑编排器”。
- 用户不能自由拉任何线，新增下游必须遵守合法连接规则。
- 节点、边、绑定、启动、测试、运行控制都必须是真实能力，不允许做装饰性入口。
- 所有实时指标、运行进度、链路状态、监控曲线必须来源于实时采样或运行中内存态。
- 不允许用落盘快照、单点重复、伪曲线、伪进度来制造“看起来在运行”的视觉效果。
- 拓扑与 Agent 的关系必须是设计重点，不能只画节点图，不画绑定、运行、控制语义。
- 整体视觉必须延续当前运维平台蓝系工作台风格，但要在状态、风险、模式、运行结果上做明确色彩分层。

## 3. 模块核心语义

### 3.1 三层对象模型

- 拓扑节点：业务/架构语义节点，是画布中的主对象，例如 `gateway-cn-1`、`auth-cn-1`、`game-cn-1`。
- Agent：远端控制执行主体，负责上报指标、接收任务、执行远端动作。
- 服务实例：Agent 实际管理的服务或服务器实例，是拓扑节点落地运行时可绑定的实际目标。

### 3.2 节点与 Agent 的关系

- 一个拓扑节点必须支持“未绑定 Agent”“绑定主 Agent”“绑定服务实例”三种状态。
- 设计上必须清楚区分：
  - 这是业务节点
  - 这个节点当前由哪个 Agent 执行和上报
  - 这个节点最终落到哪个服务实例
- 节点编辑弹窗里，`主 Agent` 是一级绑定字段。
- 若支持服务绑定，设计上要体现“服务绑定优先于纯 Agent 绑定”的关系。
- 节点列表与节点卡片都需要可感知绑定状态，而不是只在弹窗里可见。

### 3.3 结构化拓扑的含义

- 节点新增下游不是任意连接，而是“系统给出合法候选”。
- 合法候选包含两类：
  - 已存在节点
  - 基于模板新建的节点
- 系统根据节点角色、节点语义类型、上下游规则自动判断是否允许连接。
- 系统自动为结构化拓扑重新布局。

## 4. 设计拆解清单

### 4.1 页面外壳与宽度

- 左侧为平台级导航栏。
- 右侧为模块主工作区。
- 主工作区顶部为 Hero 区，下面是规则提示条，再下面是“左侧控制台 + 右侧画布”的工作区布局。
- 页面必须支持大画布场景，不能被普通管理后台窄栏布局挤压。

### 4.2 左侧导航

- 分组必须保留平台结构：
  - 工作台
  - 架构编排
  - 执行与诊断
  - 治理与合规
- 当前激活项是“拓扑编排”。
- 需要支持从拓扑编排跳转到 `Agent 与服务器`、`动作执行`、`节点诊断` 等关联模块。

### 4.3 顶部 Hero / 标题区

- 标题：拓扑编排工作区
- 副标题：强调“结构化服务器架构编排”“点击节点右侧 + 添加合法下游”“系统自动布局并绘制链路”
- 右侧动作：
  - 返回总览
  - 项目筛选输入框
- 这是模块的定位区，不应被弱化为普通面包屑标题。

### 4.4 规则提示条

- 提示当前页面是“拓扑编排”。
- 明确说明：
  - 节点右侧 `+` 用于添加合法下游
  - 节点或边上的 `-` 用于删除
  - 系统会保护关键链路
- 设计上应是一条高可见但不压迫的说明条。

### 4.5 左侧控制台

- 必须有 3 个一级页签：
  - 工具
  - 模式
  - 节点
- 一级页签是工作方式切换，不是内容 Tab 装饰。
- 不同页签内容高度不同，设计上需兼容高密度操作区。

### 4.6 主画布与日志区

- 主画布是工作核心区域。
- 画布需要支持：
  - 网格背景
  - 平移缩放
  - 节点卡片层
  - SVG 连线层
  - 框选区域
- 画布下方必须保留运行日志区，不能省略。

## 8. 结构化编排规则

### 8.1 新增下游

- 用户必须从节点右侧 `+` 打开结构化新增菜单。
- 菜单内容必须分两组：
  - 已有节点候选
  - 可新建模板候选
- 只能显示合法候选，不显示非法连接项。

### 8.2 合法连接规则

- 由节点角色、节点类型、允许上下游角色共同决定。
- 非法连接必须明确给出失败反馈。
- 关键错误语义包括：
  - 当前角色关系不允许连接
  - 端点无效
  - 端口不存在
  - 端口容量已满
  - 重复连线
  - 语义类型不允许该方向连接

### 8.3 删除保护

- 删除边时，若边属于关键链路，应阻止删除。
- 删除节点时，若节点属于关键节点，应阻止删除。
- 删除节点成功后，应同步删除相关边和绑定关系。

### 8.4 自动布局

- 结构变更后系统自动进行 structured layout。
- 设计上要支持：
  - 结构紧凑排布
  - 自左向右的主链路阅读顺序
  - 节点层次清晰
  - 边尽量少交叉

## 13. 日志与可观测性设计

### 13.1 模式日志区

- 显示保存、删除、运行、测试、自动绑定、蓝图应用等动作日志
- 日志按时间倒序
- 日志需要支持等级：
  - 信息
  - 提示
  - 失败

### 13.2 JSON 明细区

- 用于展示接口原始返回
- 适合排查运行、测试、保存、校验失败原因

### 13.3 实时指标设计要求

- 节点卡片中的 CPU / MEM / QPS 必须区分：
  - 有真实数据
  - 无数据
  - 数据过期
- 边上的 TPS / 延迟 / 错误率必须区分：
  - 有实时链路采样
  - 仅结构已配置但暂无采样
  - 运行失败导致无法采样

### 13.4 当前实现的风险提示

- 当前代码中的边指标仍存在 synthetic fallback 逻辑。
- 新设计必须明确预留“暂无实时链路数据”空态，不应假定所有边始终有真实曲线或实时值。

## 14. 与 Agent 的关联设计

### 14.1 设计师必须理解的关系

- 拓扑节点不是 Agent。
- Agent 不是服务实例。
- 一个节点的运行与观测，依赖于其绑定的 Agent 或服务实例。
- 节点是否可远端启动，依赖：
  - 是否绑定 Agent
  - Agent 是否在线
  - 远程端口是否有效
  - endpoint 是否有效

### 14.2 节点侧必须体现的 Agent 信息

- 当前绑定 Agent 名称或 ID
- Agent 在线/离线状态
- 最后心跳或实时可用性
- 远端启动端口
- 通信地址
- 是否已绑定到具体服务实例

### 14.3 画布上建议体现的 Agent 语义

- 节点卡片需至少有一块“绑定状态区”。
- 节点未绑定时需要显式空态，不可隐藏。
- 绑定失败、Agent 离线、心跳过期必须有风险反馈。
- 同一 Agent 管理多个拓扑节点时，设计上要预留聚合信息提示方式。

### 14.4 自动绑定与人工绑定的区别

- 自动绑定：系统按规则尝试匹配
- 人工绑定：用户在节点编辑弹窗中明确指定
- 设计上应体现绑定来源，以减少误判

### 14.5 Agent 与运行态指标的关系

- 节点实时指标优先来自绑定 Agent 的实时采样。
- 如果节点没有绑定 Agent，则无法显示可信实时指标。
- 若有多个 Agent 共用同一设备，可能存在设备级聚合指标；设计上要区分“节点指标”和“设备指标”。

- Error
- Disabled

## 17. 颜色语义建议

### 17.1 保持整体风格

- 主基调仍以平台蓝系为主。
- 不可为了状态区分把页面做成高饱和拼色板。

### 17.2 推荐色彩分层

- 主操作：蓝色
- 成功动作与正常运行：绿色
- 观察态与等待态：黄色/橙色
- 风险动作如删除、停止、断开：红色
- 次级说明、辅助字段、空态：灰蓝中性色

### 17.3 节点角色色

- 不同角色节点可保留轻量角色色边框/头部渐变
- 角色色不能覆盖业务状态色语义

### 17.4 模式色

- 编辑模式：平台蓝
- 运行模式：偏绿色或蓝绿
- 测试模式：偏紫蓝或青蓝
- 必须保证模式色与风险色不冲突

## 18. 空态、错误态、禁用态要求

### 18.1 空态

- 没有节点时要有“开始创建拓扑”的引导
- 没有绑定时要有“去绑定 Agent/服务”的引导
- 没有实时数据时要有“暂无实时采样”的说明

### 18.2 错误态

- 非法连接
- 删除受保护对象
- 蓝图应用失败
- 绑定失败
- 远端启动失败
- 运行失败
- 测试失败

### 18.3 禁用态

- 运行模式下禁用结构编辑
- 测试模式下禁用结构编辑
- 模式锁定后禁用切换
- 未选中边时禁用删除边
- 节点未绑定时禁用远端启动

## 19. 鼠标与键盘交互

- 滚轮：缩放
- `Space + 拖拽`：平移
- `Ctrl/Cmd + 0`：重置视图
- 框选：批量选中节点
- 点击节点：打开编辑
- 点击边：选中边
- `Delete`：
  - 优先删除选中边
  - 其次删除选中节点
- `Escape`：
  - 关闭结构化新增菜单
  - 关闭节点编辑弹窗

## 21. 设计交付重点提醒

- 这不是“一个流程图页面”，而是一整套运维编排工作台。
- 设计重点不能只放在画布，要同时覆盖：
  - 控制台
  - 节点资产库
  - 结构化新增
  - 节点编辑
  - Agent 绑定
  - 服务绑定
  - 远端启动
  - 运行模式
  - 测试模式
  - 日志观察
  - 实时指标与空态
- 拓扑与 Agent 的关系必须在设计稿中被清晰可视化，不然开发后用户仍会分不清“节点”“Agent”“服务实例”。

## 22. 当前实现与后续设计注意事项

- 当前真实代码已经具备结构化拓扑、绑定、远端启动、运行控制、测试、日志、蓝图等能力。
- 当前模板与脚本中仍有历史乱码文案，设计稿应以本 spec 的规范中文为准，不应继承源码里的乱码。
- 当前边指标存在 synthetic fallback 风险，后续实现应按“无实时数据空态”重做，不应在设计稿里默认所有边都有实时数值。
- 设计师出图时，必须同时考虑：
  - 真正有数据时如何显示
  - 没数据时如何显示
  - 失败时如何反馈
  - 禁用时如何降级
